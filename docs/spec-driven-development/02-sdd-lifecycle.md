# 02. SDD 生命周期（面向 AI 自动编码）

## 1. 生命周期总览

```text
Intake -> Feature Spec -> Technical Design -> Task Plan -> AI Coding -> Verification -> Release -> Learn
```

## 2. 分阶段定义（含 DoR/DoD）

### Phase 0: Intake（需求进入）

**输入**：业务目标、问题陈述、约束（性能/兼容/资源/时间）。

**DoR（可进入下一阶段）**：

- [ ] 目标可量化（例如吞吐 +20%、P95 不劣化）。
- [ ] 明确“谁受益、如何验证”。

### Phase 1: Feature Spec

**输出**：`feature-spec.md`。

**至少包含**：范围、非目标、用户行为、失败语义、验收标准。

**DoD**：

- [ ] In Scope / Out of Scope 明确。
- [ ] 验收标准可转测试用例（AT 编号）。

### Phase 2: Technical Design

**输出**：`technical-design.md`。

**至少包含**：模块影响、接口与配置、数据/控制流、并发一致性、风险回滚。

**DoD**：

- [ ] 关键链路有时序图或流程描述。
- [ ] 配置项变更包含默认值与兼容策略。
- [ ] 对 P0/P1 变更给出回滚方案。

### Phase 3: Task Plan

**输出**：`task-plan.md`。

**至少包含**：任务拆解、依赖、测试任务、完成定义。

**DoD**：

- [ ] 每任务映射 `FS/TD/AT`。
- [ ] 存在独立测试任务，不与实现混写。

### Phase 4: AI Coding

**输入**：Spec + Design + Task。

**执行要求**：

- 先复述本次实现的条目编号。
- 只实现计划内任务；超范围必须先发起 SCP（规格变更提案）。
- 每次变更输出受影响文件与测试命令。

### Phase 5: Verification

按风险级别执行测试矩阵：

- P0：单测 + 集成 + 性能冒烟 + 静态检查。
- P1：单测 + 场景集成 + 静态检查。
- P2：单测或文档检查。

### Phase 6: Release & Learn

发布后回写：

- 规格偏差（Spec Drift）；
- 线上观测结果；
- 下次模板改进点。

## 3. 规格变更提案（SCP）

触发条件：

- 新增接口或配置；
- 默认行为变更；
- 性能预算改变；
- 兼容性承诺变化。

模板（最小字段）：

1. 变更原因；
2. 受影响条目（旧 -> 新）；
3. 风险与缓解；
4. 迁移与回滚步骤。

## 4. AI 协作固定前缀（建议）

```text
先列出你要实现的 FS/TD/AT 编号。
若发现规格缺失，先输出 SCP 草案，不直接编码。
输出按以下顺序：计划 -> 代码 -> 测试 -> 风险与回滚。
```
