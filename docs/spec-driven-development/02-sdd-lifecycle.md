# 02. SDD 生命周期（面向 AI 自动编码）

## 1. 生命周期阶段

### Phase 0: Intake（需求进入）

输入：问题陈述、业务目标、约束（兼容性/时延/资源预算）。
输出：需求卡片（1 页）。

### Phase 1: Feature Spec（功能规格）

输入：需求卡片。
输出：`feature-spec.md`，重点定义：

- In scope / Out of scope；
- 用户可见行为；
- 异常与失败语义；
- 验收标准（Given-When-Then）。

### Phase 2: Technical Design（技术规格）

输入：`feature-spec.md`。
输出：`technical-design.md`，重点定义：

- 影响模块（按目录）；
- 数据流、控制流、并发模型；
- 接口契约与配置变更；
- 性能预算、风险、回滚策略。

### Phase 3: Task Plan（实现计划）

输入：`technical-design.md`。
输出：`task-plan.md`，重点定义：

- 按提交粒度拆分的任务；
- 每任务对应测试与验收点；
- 依赖关系与并行策略。

### Phase 4: AI Coding（自动编码）

输入：Spec + Design + Task。
输出：代码变更与测试变更。

要求：每次 AI 生成必须声明“对应 spec 条目编号”。

### Phase 5: Verification（验证）

执行单测、集成测试、静态检查、性能冒烟。

### Phase 6: Release & Learn（发布与沉淀）

沉淀偏差项：

- 规格未覆盖但实现中出现的问题；
- 回滚/灰度经验；
- 后续规范更新点。

## 2. AI 协作协议（建议作为固定提示词前缀）

```text
你必须先复述本次任务涉及的 Spec 条目编号，再给出实现方案。
你不得实现 Spec 之外的行为，除非先提交“Spec Change Proposal”。
你必须给出测试清单，并将每条测试映射到对应验收标准编号。
```

## 3. 规格变更控制（Spec Change Proposal, SCP）

触发条件：

- 新增接口/配置；
- 变更默认行为；
- 性能预算调整；
- 兼容性承诺变化。

最小内容：

1. 变更原因；
2. 原规格条目与新条目对照；
3. 风险评估；
4. 迁移与回滚策略。

## 4. 质量门禁建议

- 必选门禁：编译通过 + 受影响模块单测通过。
- 条件门禁：涉及协议或跨模块时执行集成测试。
- 推荐门禁：关键路径（写入/查询）性能对比不劣化。
